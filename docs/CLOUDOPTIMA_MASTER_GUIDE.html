Step 1: Start Here — Get Up and Running (5 minutes)

GOAL
Clone the repo, install dependencies, run the app, see it working. Do this before anything else.

1.1 Clone and Setup

Open your terminal and run these commands one by one:

# Download the project
git clone https://github.com/G-Narendra/CloudOptima
cd CloudOptima

# Create a virtual environment (isolates our dependencies)
python -m venv venv

# Activate it
source venv/bin/activate        # On Linux/Mac
# venv\Scripts\activate         # On Windows

# Install everything we need
pip install -r requirements.txt

# Copy the environment template (no API key needed for demo mode)
cp .env.example .env
Why a virtual environment?
Without it, installing packages pollutes your global Python installation. Different projects might need different versions of the same library. A venv keeps each project isolated. If something breaks, just delete the venv folder and recreate it.

1.2 Run the App

streamlit run dashboard.py

This starts the web app. Open http://localhost:8501 in your browser. You should see the CloudOptima dashboard.

What you'll see: A form asking for:

  • Project name — e.g., "Patient portal for UAE hospitals"
  • Workload type — e.g., "Real-time data processing"
  • Azure region — pick from dropdown (UAE North, Central India, etc.)
  • Compliance — pick from dropdown (UAE PDPL, India DPDP, etc.)
  • Scale — Small, Medium, Large
  • Monthly budget — enter a number
  • Services and context — optional details

1.3 Run the Tests

Before you change any code, run the tests to make sure everything works:

pytest tests/ -v

You should see 205+ tests pass. If they don't, check that your environment is set up correctly.

Q: Why 205+ tests? Isn't that overkill for a student project?
No — and here's why. Early versions had zero tests. Every change risked breaking something. When we added the Pydantic validation pipeline, we broke the session creation flow without realizing it for 3 days. Now each test file covers a critical path: models, orchestration, compliance rules, pricing data, LLM cache, health checks, error tracking, and observability. When all 205 pass, we know the core system works.

1.5 What Just Happened?

Behind the scenes, this pipeline executed:

User submits form
    --> Input sanitized (XSS protection)
    --> Session created with unique ID
    --> Architect agent generates design (compute, storage, network, data)
    --> Cost analyst evaluates pricing (identifies conflicts with Architect)
    --> Security engineer assesses vulnerabilities (identifies conflicts)
    --> Compliance officer checks regulations (identifies conflicts)
    --> Orchestrator detects conflicts across 6 agent pairs
    --> Judge resolves each conflict (binary decisions)
    --> 5 artifacts generated (IaC, cost, compliance, rationale)
    --> Results displayed in dashboard with KPI cards

Everything completed in <1 second because we're in demo mode — no real API calls are made. The mock responses are realistic enough to demonstrate the full workflow.

The text version (for quick reference):

Step 1: You fill in the form
Step 2: Input is sanitized (no XSS, no injections)
Step 3: A Session is created with a unique UUID
Step 4: Agents run one by one:
   a. ARCHITECT: Designs compute, storage, network, and data tiers
   b. COST ANALYST: Estimates pricing, finds savings, flags conflicts
   c. SECURITY ENGINEER: Assesses vulnerabilities, flags conflicts
   d. COMPLIANCE OFFICER: Checks regulations, flags conflicts
Step 5: Orchestrator detects conflicts (6 possible pair combinations)
Step 6: JUDGE resolves each conflict with a binary decision
Step 7: 5 artifacts are generated (IaC, cost forecast, etc.)
Step 8: Results appear in the dashboard
Q: Why run agents sequentially instead of in parallel?
Each agent after the Architect needs to see the Architect's design to evaluate it. The Cost Analyst can't find pricing conflicts without knowing what the Architect proposed. But within each agent, the LLM call could run in parallel with other non-dependent work. For the demo mode (no real API calls), sequential execution is instant anyway.

2.4 Core Architecture Components

The Adversarial Arbitration Engine (The Secret Sauce)

This is what makes CloudOptima different from every other AI architecture tool. Instead of averaging opinions (which produces vague, middle-ground recommendations), we use adversarial arbitration:

  • Each agent advocates uncompromisingly for its domain
  • Each non-Architect agent explicitly reports conflicts with the Architect's design
  • The Orchestrator detects conflicts across 6 agent pairs
  • The Judge makes a binary decision for each conflict: OVERRULE one agent, SUSTAIN the other, or PARTIAL OVERRIDE

Why binary? Because you can't average compliance: Data either stays in-region or it doesn't. Data is either encrypted at rest or it isn't. You either have 99.95% SLA or you don't. Compromise positions often violate requirements.

The Pydantic Validation Pipeline

LLM outputs produce malformed JSON about 20% of the time. Our pipeline handles this gracefully:

def validate_agent_output(output_text, agent_type):
    # 1. Extract JSON from code fences
    # 2. Parse with json.loads()
    # 3. Validate against Pydantic schema
    # 4. If anything fails: log error, return partial data
    #    NEVER CRASH. The session continues with what it has.

Key principle: Never crash on validation failure. The dashboard shows partial results, and the Judge accounts for missing agent output.

The Two-Tier Compliance System

Tier 1: 21 hardcoded compliance rules across 4 frameworks (India DPDP, EU GDPR, US HIPAA, UAE PDPL). These give zero-latency, guaranteed-accurate checks for the most common use cases.

Tier 2: ChromaDB vector store for unknown regions. Queried via sentence-transformers embeddings when the hardcoded rules don't cover a region.

The Two-Tier Pricing System

Static DB: 4 regions x 100+ Azure SKUs with real pricing data. Instant lookups, zero network calls.

Live API: Calls prices.azure.com (public, no auth) for prices outside our database. Results are cached. Falls back to static DB on failure.

Step 3: What We Learned — Lessons from Building

GOAL
Learn from our mistakes so you don't repeat them. This is what we'd tell our past selves.

3.1 The 105-Second Disaster (Our Biggest Failure)

Timeline: We deployed to Streamlit Cloud. First demo with friends: 98 seconds for a response. Next session: 105 seconds.

Root cause: 3 lines of code:

class NVIDIAClient:
    def chat_completion(self, messages):
        if settings.demo_mode:          # <--- Was False on Streamlit Cloud
            return self._mock_response(messages)
        # ... try real API with 60s timeout ...  # <--- Always hit this

The DEMO_MODE environment variable was never set on Streamlit Cloud. Every request made a real API call. NVIDIA's API doesn't work well from Streamlit's restricted network — each call timed out after 60 seconds. Then tenacity retried 3 times (2s + 4s + 8s). For 5 agents, worst case was 370 seconds.

The fix was 3 layers deep:

  • Layer 1: Removed the API call path entirely. Made chat_completion() always return mock data.
  • Layer 2: If we re-enable it later, timeout drops from 60s to 5s, retries from 3 to 1.
  • Layer 3: Fixed Material icon rendering that was showing up as raw text.
THE META-LESSON: Deploy early, deploy often
We tested locally with a working API key (everything was fast). Deployed to Streamlit Cloud (API was blocked). Never noticed because demo mode defaulted to false. The bug would have been caught in 5 minutes if we'd deployed on day 1. Always test on your target platform.

3.2 Five Critical Mistakes We Made

Mistake 1: Time-based session IDs
We used session_20240725_143022 format. Two sessions created in the same second had the same ID. Data corruption. Fix: uuid.uuid4().hex[:12] — 16^12 unique values. Lesson: Never use time-based IDs for concurrent systems.
Mistake 2: Naive datetimes
We used datetime.utcnow() — returns a naive datetime (no timezone). Comparing naive vs aware datetimes raises TypeError. Sorting sessions broke. JSON serialization failed. Fix: datetime.now(timezone.utc). Lesson: Always use timezone-aware datetimes. No excuse in 2026.
Mistake 3: 60-second HTTP timeouts
Default timeout for httpx is 60 seconds. On Streamlit Cloud's restricted network, every API call waited a full minute before failing. Fix: Set timeouts aggressively (3-5s) for serverless apps. Fail fast to mock data.
Mistake 4: No gitignore for .env
Committed .env with real NVIDIA API keys to a public GitHub repo. A bot scraped them within 30 minutes. NVIDIA revoked the key. Fix: Set up .gitignore before the first commit. Use .env.example as a template.
Mistake 5: Regex-based JSON extraction
Used re.search(r'\{.*\}', text) to extract JSON from LLM outputs. Broke when string values contained braces. Fix: Multi-stage extraction: try ```json fence first, then bare ``` fence, then regex as last resort.

Q&A: Common Questions

Q: Why 5 agents? Why not 3 or 7?
The Azure Well-Architected Framework defines 5 pillars. Our agents map directly: Architect (Performance + Operational Excellence), Cost (Cost Optimization), Security (Security), Compliance (Reliability), Judge (Cross-pillar arbitration). With 4 specialists we have 6 conflict pairs — tractable. With 6 specialists we'd have 15 pairs — overwhelming.
Q: Why Streamlit and not Next.js / React?
Speed of development. Our team knows Python, not frontend frameworks. We built a working dashboard in 2 days. Trade-off: harder to customize complex interactions. If needed, we'd migrate to Next.js + FastAPI — the FastAPI backend at src/api/main.py is already in place.
Q: Is the compliance advice legally accurate?
No — and we explicitly say so. Every compliance assessment includes the disclaimer: "This output is decision support for a design exercise, not legal advice." The rules are simplified from public regulatory text. Real compliance requires a human expert.
Q: Why in-memory storage instead of a database?
Zero setup, O(1) lookups, easy debugging. 100 concurrent sessions use less than 50 MB RAM. For production, we'd migrate to Azure Cosmos DB or Redis — the Pydantic models are already serializable, so migration is straightforward.
Q: Can I add a 6th agent?
Yes, in about 50 lines of code. See section 5.3 for the exact steps. The BaseAgent, validation pipeline, and conflict detection all work automatically.

1. Executive Summary

1.1 What Is CloudOptima?

CloudOptima is a multi-agent AI system that simulates a panel of five cloud infrastructure experts to design, cost, secure, and validate Azure architectures. A user describes their infrastructure needs in plain English, and five specialized AI agents (Architect, Cost Analyst, Security Engineer, Compliance Officer, and Judge) analyze the requirements, produce domain-specific assessments, detect conflicts between their recommendations, and resolve those conflicts through structured arbitration.

3. Data Model Deep Dive

3.1 Models Overview (src/core/models.py)

All data models use Pydantic BaseModel (v2). We chose Pydantic over:

  • dataclasses: No built-in validation, no serialization methods
  • attrs: Less ecosystem support; Pydantic has broader adoption
  • Plain dicts: No type safety, no IDE autocomplete, runtime errors
  • marshmallow: More verbose; requires separate schema classes

Pydantic gives us:

  1. Validation at instantiation: Type errors caught immediately, not at runtime
  2. Serialization/deserialization: model_dump() and model_validate() built-in
  3. JSON Schema generation: Automatic OpenAPI-compatible schemas
  4. Nested model validation: ArchitectResponse.architecture.compute.recommendation must be a string
  5. Default factories: Field(default_factory=lambda: _unique_id("session_")) for auto-ID generation

3.2 Core Entities

class Session(BaseModel):
    """A single design session tracking one user request through its lifecycle."""
    id: str = Field(default_factory=lambda: _unique_id("session_"))
    status: SessionStatus = SessionStatus.PENDING
    requirement: Optional[Requirement] = None
    created_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))
    updated_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))
    user_id: str = "demo_user"
    region: str = ""
    duration_seconds: Optional[float] = None

Why UUIDs with prefix? Earlier versions used datetime-based IDs (session_20240725_143022), which caused collisions when sessions were created rapidly (common during testing). The current approach uses uuid.uuid4().hex[:12] — first 12 hex characters of a UUID4 — prefixed with a human-readable label. This gives:

  • Uniqueness: 16^12 = 2.8 × 10^14 possible values per prefix
  • Human readability: session_a7b7d2c61fc0 is clearly a session ID
  • No sequential enumeration: Attackers cannot guess session IDs

Why datetime.now(timezone.utc) instead of datetime.utcnow()? The latter is deprecated in Python 3.12+. Using timezone.utc at creation time ensures timezone-aware datetimes, preventing:

  • Ambiguity between UTC and local time
  • Comparison errors in sorted lists
  • Serialization issues (naive datetimes don't have timezone info)

Why str, Enum instead of plain Enum? This is a StrEnum — the values are strings, enabling:

  • Direct comparison with string config values: agent_type == "architect"
  • JSON serialization without custom encoders
  • Database storage as VARCHAR

Why these 5 agents specifically? The Azure Well-Architected Framework defines 5 pillars: Reliability, Security, Cost Optimization, Operational Excellence, Performance Efficiency. Our agents map to:

  • Architect → Performance Efficiency + Operational Excellence
  • Cost Analyst → Cost Optimization
  • Security Engineer → Security
  • Compliance Officer → Reliability (regulatory compliance)
  • Judge → Cross-pillar arbitration

This covers all 5 WAF pillars while keeping the agent count manageable. Each agent has a clearly bounded domain of expertise.

3.5 The Requirement Model

class Requirement(BaseModel):
    raw_text: str                    # Original user input
    workload_description: str = ""   # Extracted workload type
    target_region: str = ""          # Azure region
    compliance_frameworks: list[str] = Field(default_factory=list)
    estimated_scale: str = ""        # small/medium/large/enterprise
    key_services: list[str] = Field(default_factory=list)
    special_constraints: list[str] = Field(default_factory=list)

Why not extract entities via NLP? Initially, we considered using spaCy or a dedicated NER model to extract regions, services, and constraints from user text. We abandoned this because:

  1. Latency: Adding an NLP pipeline would add 500ms–2s per request with minimal benefit
  2. Accuracy: LLMs already do this implicitly during the analysis
  3. Complexity: Maintaining NLP models adds deployment and dependency costs
  4. Cost: Free alternatives (spaCy) are large models; cloud NLP APIs cost money

Instead, we use the form-based approach: users explicitly select region, compliance frameworks, and scale from dropdowns. This is faster, more accurate, and requires zero ML infrastructure.

4. Agent Architecture & System Prompts

4.1 BaseAgent Class (src/core/agent_base.py)

class BaseAgent:
    def __init__(self, agent_type: AgentType, model: Optional[str] = None):
        self.agent_type = agent_type
        self.model = model
        self.client = NVIDIAClient(model=model)
        self.system_prompt = SYSTEM_PROMPTS[agent_type]

Why a single BaseAgent instead of 5 separate classes? Two reasons:

  1. Consistency: All agents follow the same lifecycle: build messages → call LLM → parse output → validate → return AgentTurn. Having separate classes would duplicate this logic 5 times.
  1. Extensibility: Adding a 6th agent (e.g., "Sustainability Officer") requires only:
  • 1 new entry in AgentType enum
  • 1 new system prompt in SYSTEM_PROMPTS
  • 1 new Pydantic schema in agent_schemas.py
  • 1 new registry entry in AGENT_RESPONSE_SCHEMAS

That's ~50 lines total for a new agent. The BaseAgent handles execution automatically.

Why the model parameter? Per-agent model overrides. During testing, we found that the Compliance Officer performs better with a larger model (more regulatory knowledge) while the Cost Analyst can use a smaller model (simple arithmetic). The Settings.get_agent_model() method provides this:

def get_agent_model(self, agent_type: str) -> str:
    override_map = {
        "architect": self.architect_model,
        "cost": self.cost_model,
        "security": self.security_model,
        "compliance": self.compliance_model,
        "judge": self.judge_model,
    }
    return override_map.get(agent_type) or self.nvidia_model

This allows fine-grained cost/quality trade-offs without changing code.

4.2 System Prompt Design Philosophy

Each system prompt follows a structured format:

  1. Role Definition: "You are an Azure Solutions Architect..."
  2. Knowledge Boundary: What the agent knows and doesn't know
  3. Output Schema: Exact JSON structure with field descriptions
  4. Constraints: Nuance, disclaimers, prohibited behaviors

Architect Prompt

"You are an Azure Solutions Architect... Follow the Azure Well-Architected Framework
principles: Reliability, Security, Cost Optimization, Operational Excellence,
Performance Efficiency."

Why the Well-Architected Framework? It's Microsoft's canonical architecture methodology. Teaching the LLM to follow WAF principles ensures:

  • Industry alignment: The output matches what real Azure architects would produce
  • Measurable quality: Each recommendation can be traced to a WAF pillar
  • Audit trail: Compliance teams can verify output against recognized standards

Cost Analyst Prompt

"You are an Azure FinOps / Cost Optimization Analyst... Be quantitative. Use realistic
Azure pricing data. Flag any cost-inefficient recommendations."

Why "conflicts_with_architect" as a first-class output field? We explicitly ask each non-architect agent to identify disagreements with the Architect's design. This:

  1. Forces adversarial thinking: Compliance must explicitly say "Architect's GRS violates DPDP"
  2. Structures conflict detection: The orchestrator parses conflicts_with_architect to create Conflict objects
  3. Prevents silo thinking: No agent can ignore another agent's domain

Compliance Officer Prompt — The Most Complex

This prompt is the longest because it contains:

  1. Curated regulatory knowledge: 4 frameworks with specific sections
  2. Knowledge boundary: "For regions not covered above, the system has a RAG engine..."
  3. Disclaimer requirement: "Your output is DECISION SUPPORT, not legal advice"
  4. Citation requirement: "Be specific about which regulation and section applies"

Why embed regulations directly instead of always using RAG? For the 4 most common frameworks (GDPR, HIPAA, DPDP, PDPL), we bake the knowledge into the prompt because:

  • Zero latency: No vector DB query needed
  • Guaranteed accuracy: No retrieval errors for well-known frameworks
  • Lower cost: RAG queries add API calls and token costs
  • Testable: The knowledge is static and verifiable in unit tests

For less common regions, the RAG engine kicks in automatically.

Judge Prompt — The Arbitration Engine

"You are the Judge in a multi-agent architecture panel... Your arbitration must be:
1. TRACEABLE - Reference each agent's specific position
2. EXPLAINABLE - Provide a clear rationale for each decision
3. BALANCED - Give each agent's argument fair consideration
4. BINARY - For each conflict, explicitly state which agent is overruled"

Why binary resolution instead of compromise? In cloud architecture, many conflicts cannot be averaged:

  • Data either stays in-region or it doesn't (binary)
  • Data is either encrypted at rest or it isn't (binary)
  • You either have 99.95% SLA or you don't (binary)

Compromise positions often violate requirements. The binary approach forces the Judge to make a clear decision, which is more useful than a hedged recommendation.

4.3 Why These Prompts Are Effective

The prompts were refined through 50+ iterations. Key lessons:

  1. Explicit JSON schemas work better than descriptions: "Output as JSON" produces malformed JSON; providing the exact structure with \\n escapes produces valid JSON 95%+ of the time.
  1. Negative examples help: The Judge prompt includes "Do NOT silently average conflicting positions" — this was added after early versions produced vague compromise recommendations.
  1. Role priming matters: Starting with "You are an Azure Solutions Architect" (specific, credentialed) performs better than "You will design cloud infrastructure" (generic, task-oriented).
  1. Knowledge boundaries prevent hallucination: The Compliance prompt explicitly says "This output is decision support for a design exercise, not legal advice" — this disclaimer appears in every response, preventing user over-reliance on potentially incorrect compliance suggestions.

Why tenacity instead of custom retry logic? Building retry logic manually is error-prone:

6. Pydantic Validation Engine

6.1 Why Pydantic Validation? (src/core/agent_schemas.py)

This module was born from a critical bug: LLM outputs were producing malformed JSON ~20% of the time, causing the entire session to fail. We needed a robust parsing pipeline that:

  1. Handles malformed JSON gracefully (never crashes)
  2. Extracts JSON from markdown code fences
  3. Validates structure against expected schemas
  4. Fills missing fields with defaults
  5. Logs errors for debugging without failing the session

6.2 JSON Extraction Pipeline

def extract_json_from_llm_output(output_text: str) -> str:
    # 1. Try ```json ... ```  (most common LLM output format)
    if "```json" in output_text:
        return output_text.split("```json")[1].split("```")[0].strip()
    
    # 2. Try ``` ... ``` (plain code fence)
    if "```" in output_text:
        return output_text.split("```")[1].split("```")[0].strip()
    
    # 3. Try to find a JSON object anywhere in the text
    match = re.search(r"\{.*\}", output_text, re.DOTALL)
    if match:
        return match.group()
    
    # 4. Last resort: return as-is
    return output_text.strip()

Why this order? LLMs typically output JSON in \\\\\\json ... \\\\\\` blocks. The extraction tries the most specific pattern first (exact match) and falls back to less specific patterns. This gives us:

  • ~95% success on well-formatted LLM output
  • ~80% on poorly formatted output
  • Never crashes (last resort returns raw text)

Why not use a JSON repair library like json-repair? We evaluated json-repair but found:

  • Additional dependency (maintenance burden)
  • 50-200ms per repair call (latency cost)
  • Still fails on ~10% of cases
  • Pydantic defaults already handle missing fields

6.4 Validation Function

def validate_agent_output(output_text: str, agent_type: AgentType) -> dict:
    schema = AGENT_RESPONSE_SCHEMAS.get(agent_type)
    if not schema:
        return {"raw_response": output_text}

    try:
        json_str = extract_json_from_llm_output(output_text)
        parsed = json.loads(json_str)
        validated = schema.model_validate(parsed)
        return validated.model_dump(exclude_none=False)
    except json.JSONDecodeError as e:
        logger.warning(f"JSON decode failed for {agent_type}: {e}")
        return {"raw_response": output_text, "_error": f"JSON decode failed: {e}"}
    except ValidationError as e:
        logger.warning(f"Pydantic validation failed for {agent_type}: {e}")
        return {"raw_response": output_text, "_error": f"Validation failed: {e}"}
    except Exception as e:
        return {"raw_response": output_text, "_error": str(e)}

Why never crash? A validation failure should never bring down the entire session. The graceful degradation model:

  1. Logs the error (for debugging)
  2. Returns a dict with _error key (for dashboard display)
  3. Continues the session (so partial results are still visible)
  4. The Judge sees the error and can account for missing agent output

  3. Natural interaction: In real architecture reviews, the initial design is reviewed against each domain independently

The orchestrator constructs the 6 conflict pairs from these single-perspective reports.

7.2 Conflict Detection Algorithm

Input: 4 validated agent outputs (Architect, Cost, Security, Compliance)
Output: 0-6 Conflict objects

For each of 6 agent pairs:
    1. Extract conflicts_with_architect[] from each agent's output
    2. Combine both agents' reports into one conflict summary
    3. Create Conflict object with:
       - dimension (e.g., "cost_vs_compliance")
       - agent_a_position (3 sample items from Cost)
       - agent_b_position (3 sample items from Compliance)
       - summary (human-readable description)

Why limit to 3 sample items? The agent_a_position and agent_b_position fields are used by the Judge for context. An agent might report 10+ conflicts, but passing all 10 to the Judge exceeds token limits. We truncate to 3 most relevant items — the Judge can still understand the tension without seeing every detail.

11.2 Cache Key Design

def _make_cache_key(messages: list[dict], model: str, temperature: float) -> str:
    msg_hash = _hash_messages(messages)
    return f"llm:{model}:{temperature:.1f}:{msg_hash}"

def _hash_messages(messages: list[dict]) -> str:
    serialized = json.dumps(messages, sort_keys=True, ensure_ascii=False, default=str)
    return hashlib.sha256(serialized.encode("utf-8")).hexdigest()

Why SHA256 instead of MD5 or built-in hash()?

  • SHA256: Cryptographically sufficient for uniqueness, fast enough (< 1µs per hash)
  • MD5: 128 bits → higher collision probability (1 in 2^64 vs 1 in 2^256)
  • built-in hash(): Not deterministic across Python process restarts

Why include model and temperature in the key? The same prompt produces different outputs with:

  • Different models (Mistral vs GPT-4o)
  • Different temperatures (0.2 vs 0.8)

If we keyed only on messages, switching models would return stale cached responses.

11.3 Raw Key-Value API

def get_raw(self, key: str) -> Optional[str]: ...

Why a separate raw API? The LLM cache was designed for message-based caching. Adding a raw API enabled pricing data caching without:

11.4 TTL and Eviction

def _evict_oldest(self):
    """Evict ~20% of oldest entries when cache is full."""
    evict_count = max(1, self.max_size // 5)
    keys_to_evict = list(self._data.keys())[:evict_count]
    for key in keys_to_evict:
        del self._data[key]

Why FIFO eviction instead of LRU? Python's dict preserves insertion order (Python 3.7+). For this use case, FIFO is:

  • Simple: No need for access time tracking
  • Fast: O(k) where k = eviction count
  • Adequate: Old entries (likely stale) are removed first

True LRU would require an ordered dictionary with access timestamp updates — ~50 lines of additional code for marginal benefit.

Why evict 20% instead of 1 entry? Batch eviction reduces the frequency of eviction operations. If the cache fills up frequently (e.g., during a demo), evicting 1 entry at a time means O(n) evictions to regain capacity. Evicting 20% at once means the next eviction won't happen until the cache fills again (20% more entries).

11.5 Disk Persistence

def _save_to_disk(self):
    """Write cache entries to disk as JSON (best-effort)."""
    try:
        payload = {"version": 1, "entries": serializable, ...}
        path = self._persist_path()
        with open(path, "w") as f:
            json.dump(payload, f, indent=2)
    except Exception as e:
        logger.warning(f"Failed to persist LLM cache: {e}")

Why persist every write? This is a design trade-off:

  • Pro: Cache survives app restarts, server crashes, and redeployments
  • Con: Every set/invalidate operation does file I/O (~5-10ms)

The trade-off favors persistence because:

  1. Cache entries are expensive to generate (LLM API calls cost money)
  2. Demo mode mock responses are deterministic — cache hits eliminate redundant computation
  3. The cache file is small (< 1MB for 1000 entries)

What about corruption? The _load_from_disk method handles:

  • Missing file: Start fresh
  • Invalid JSON: Log warning, start fresh
  • Expired entries: Skip, don't load
  • Any exception: Log warning, start fresh

This is "crash-only" design — the cache never leaves the system in an inconsistent state.

def sanitize_text(text, max_length=5000):
    """Strip whitespace, null bytes, enforce max length."""

def _before_send(event, hint):
    """Sanitize sensitive data before sending to Sentry."""
    # Remove local variables from stack frames
    for value in event.get("exception", {}).get("values", []):
        for frame in value.get("stacktrace", {}).get("frames", []):
            frame.pop("vars", None)
    
    # Redact sensitive request data
    request = event.get("request", {})
    request.pop("data", None)        # Remove request body
    request.pop("cookies", None)     # Remove cookies
    request.pop("headers", {}).pop("Authorization", None)
    return event

19.3 Dockerfile Design

# Multi-stage build
FROM python:3.12-slim AS builder
RUN pip install --no-cache-dir --user -r requirements.txt

FROM python:3.12-slim
COPY --from=builder /root/.local /root/.local
COPY --chown=appuser:appgroup . .
USER appuser
EXPOSE 8501
HEALTHCHECK --interval=30s --timeout=10s --start-period=15s --retries=3 \
    CMD python -c "import socket; s=socket.socket(); s.connect(('localhost',8501)); s.close()"
CMD ["streamlit", "run", "dashboard.py", "--server.port=8501", "--server.address=0.0.0.0"]

Why multi-stage build? Multi-stage builds:

  1. Reduce image size: Builder stage has gcc for compiling native extensions; runtime stage only has python:3.12-slim (no build tools)
  2. Improve security: Smaller attack surface (no compilers, no build artifacts)
  3. Faster deployments: ~200MB vs ~500MB for a single-stage build

Why non-root user? Security best practice — the container runs as appuser (UID 1001) instead of root. If the container is compromised, the attacker has limited permissions:

  • Cannot install system packages
  • Cannot modify application files
  • Cannot access other containers on the same host

Why a health check? Azure Container Apps needs health checks for:

  • Determining if the container is ready (startup probe)
  • Replacing failed containers (liveness probe)
  • Zero-downtime deployments (readiness probe)

20.2 Why 5 Agents Specifically?

Minimum viable set: The 4 Review agents (Architect, Cost, Security, Compliance) correspond to the 4 non-people Azure Well-Architected Framework pillars. The 5th agent (Judge) is the arbitration layer.

Why not 3 agents? 3 agents would cover only C(3,2) = 3 conflict pairs — missing critical tensions like Security vs Compliance.

Why not 10 agents? More agents means:

  • More LLM calls (higher latency and cost)
  • More conflict pairs (C(10,2) = 45)
  • More context for the Judge (token limits)
  • Diminishing returns in architecture quality

Empirically, 5 agents is the sweet spot where each agent has a distinct, non-overlapping domain.

21. Design Decisions: Full Trade-off Analysis

21.1 Sequential vs Parallel Agent Execution

Decision: Sequential (current) / Future: Parallel

FactorSequential (Chosen)Parallel
Conflict detectionAgents see previous outputs? No (they run independently)Same
LatencySum of all agents (10-60s)Max of all agents (3-15s)
Rate limits1 call at a timeMultiple concurrent calls
ComplexitySimple loopNeed asyncio.gather + error isolation
DebuggingEasy (one agent at a time)Harder (concurrent failures)

Why sequential for now?

  1. NVIDIA's free tier rate limits (~60 RPM) make parallel calls risky
  2. Sequential execution isolates agent failures (one fails, others complete)
  3. The mock client (demo mode) returns instantly, making parallelism unnecessary

When to switch to parallel: When rate limits are no longer a constraint (paid API keys, self-hosted models).

21.2 Adversarial Arbitration vs Consensus

Decision: Adversarial arbitration (explicit conflict resolution)

FactorAdversarial (Chosen)Consensus (Vote/Average)
QualityEach position defendedPositions are averaged
TraceabilityEvery conflict documentedNo trace of disagreement
Edge casesHandled explicitlyLost in averaging
ComplexityJudge prompt is complexSimple majority logic
ConfidenceKnow which agent was overruledDon't know if the consensus is correct

Why adversarial is better for cloud architecture: In cloud architecture, conflicts are real — using GRS when DPDP requires LRS is a literal regulatory violation. Averaging positions would give a "partial GRS, partial LRS" recommendation that neither satisfies compliance nor provides redundancy.

21.3 JSON Code Fences vs Plain Text

Decision: Output JSON in \\\\\\`json blocks

FactorCode Fences (Chosen)Pure JSONMarkdown Tables
LLM compliance95%+ success~70% (injects extra text)~60% (struggles with tables)

Parser complexityEasy (split on backticks)Harder (find JSON among text)Complex (table → JSON transform)
Schema validationSame JSON regardlessSame JSON regardlessNeed table schema separately

Code fences win because LLMs are trained to output JSON in this format. The extract_json_from_llm_output() function handles the extraction.

21.4 Disk-Persisted Cache vs In-Memory Only

Decision: Disk-persisted (survives restarts)

21.6 2000-char Truncation vs Full Output

Decision: Truncate agent outputs to 2000 chars for Judge context

FactorTruncated (Chosen)Full Output

The median agent output in demo mode is ~800 characters. A real LLM output might be 2000-4000 characters. Truncating to 2000 captures most decisions while keeping token costs manageable.

21.7 Pydantic Validation vs Regex Parsing

Decision: Pydantic (over initial regex approach)

This was an actual migration in the project. Initially, agent outputs were parsed with regex:

# OLD: Regex approach (brittle)
import re
cost_match = re.search(r'"estimated_monthly_cost":\s*"([^"]+)"', output)
if cost_match:
    cost = cost_match.group(1)

Problems with regex:

  1. Brittle: A slight change in JSON formatting breaks the regex
  2. No type safety: All values are strings
  3. Missing field?: Silent None return — no error handling
  4. Nested objects: Regex can't handle nested JSON gracefully
  5. Maintenance: 4 agents × 10+ fields = 40+ regex patterns

Pydantic solution:

# NEW: Pydantic approach (typed, validated)
parsed = json.loads(output)
validated = CostResponse.model_validate(parsed)
cost = validated.analysis.estimated_monthly_cost  # str, guaranteed by schema

Benefits:

  1. Type safety: Every field has a defined type (str, int, list, etc.)
  2. Default values: Missing fields get empty defaults instead of crashes
  3. Nested validation: Deeply nested objects validated at every level
  4. Error logging: ValidationError is caught and logged, not silently swallowed
  5. Extensible: Adding a field to the schema is adding one line to a Pydantic model

28. Team Workflow & Git Strategy

How the 5-person team collaborates on code. Branching strategy, PR workflow, code review standards, and sprint cadence.

28.1 Branching Strategy

We use a simplified GitHub Flow (not Git Flow) because:

  • 5 people is small enough for trunk-based development
  • No need for long-running release branches
  • Simplifies CI/CD (every branch gets tested)
  • Less merge overhead
BranchPurposeProtection
mainProduction-ready code. Deployed to AzureRequires PR review + passing CI
feature/<name>New feature or bug fixNone - created from main, merged via PR
docs/<name>Documentation-only changesSame as feature branches

28.2 Pull Request Workflow

1. Create a feature branch from main
   git checkout main && git pull
   git checkout -b feature/my-task

2. Make changes, commit frequently
   git add -A && git commit -m "[Area] Description"
   git push -u origin feature/my-task

3. Open a Pull Request against main
   - Title: [Area] Brief description
   - Description: What changed, why, how to test
   - Reviewers: At least 1 other team member

4. CI runs automatically (pytest + lint)
5. Code review: At least 1 approval required
6. Merge: Use "Squash and merge" (clean history)
7. Delete feature branch after merge

Conclusion

This Master Guide covers every component of CloudOptima in depth — from data models and algorithms to design decisions and alternatives considered. The system represents a production-grade multi-agent architecture that demonstrates:

  1. Adversarial arbitration as a better paradigm than consensus for multi-agent cloud design
  2. Pydantic-validated structured outputs for reliable LLM integration
  3. Multi-provider LLM abstraction enabling flexible model switching
  4. RAG-enhanced compliance checking with curated regulatory knowledge
  5. Disk-persisted caching for performance without cold starts
  6. Full observability with tracing, audit logging, and error tracking
  7. Graceful degradation at every level — no single point of failure
  8. Azure-native deployment path with Container Apps and cost optimization

CloudOptima was designed not just as a demo tool, but as a reference architecture for multi-agent AI systems — showing how to combine LLMs, structured validation, domain expertise, and adversarial reasoning into a reliable, production-ready application.
